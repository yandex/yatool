# Mutable storage: общий контракт и backend-библиотеки

Имеет место разделение на библиотеки:

- `base` — `Storage[T]`, стабильный `SuiteId`, метаданные;
- `in_memory` — `InMemoryStorage[T]`;
- `disk` — `DiskStorage[T]` с ленивым SQLite-индексом.

Оба backend сохраняют изменения между обращениями. `add()` передаёт владение
моделью; `add_serialized()` принимает доверенный pickle без десериализации.
`read()` выдаёт модель без права изменения, `edit()` сохраняет её при выходе,
включая исключение. Это не транзакция с rollback. Вложенные обращения к одному
ID видят одну модель; `replace()` заменяет её без смены ID. Модель и её дочерние
объекты нельзя удерживать после scope. Mutable-итератор сохраняет текущий элемент
при переходе к следующему; при раннем выходе генератор нужно явно закрывать.

In-memory хранит новые модели непосредственно. Импортированные pickle остаются
ленивыми и сохраняются обратно в память после edit. Disk дописывает snapshots
во временный spool; старые версии занимают место до закрытия. В RAM остаются
адресация, ID и активные модели, но не кэш всех результатов.

Для импортированного pickle стабильны ID и сохранённые данные, а не Python
identity модели: разные обращения могут получить разные экземпляры. Изменения
между обращениями передаются через `edit()`, а не через удержанную ссылку или
сравнение моделей через `is`. Совпадение экземпляров при вложенном обращении к
одному ID не распространяется на отдельные scopes. Resident-модели из `add()`
в in-memory backend сохраняются непосредственно; это не гарантия identity для
других способов загрузки. Основания миграции потребителей описаны в
[пакете решения](../../../docs/agents/suite_storage/2026-11-14-scoped-consumers/README.md).

`metadata(id, factory)` использует один extractor на storage. Disk создаёт индекс
при первом запросе; повторное чтение не раскрывает pickle. Изменения и замены
обновляют metadata. Адресация переключается только после успешного обновления
SQL: ошибка сериализации/SQL сохраняет предыдущие payload и metadata.
SQLite использует ограниченный page cache и MEMORY journaling для rollback.
Изменения результатов сохраняют payload, но не переписывают строку индекса,
если сами индексируемые поля не изменились; сравнение выполняет SQLite без
дополнительного heap-кэша всех метаданных.
Resident in-memory модели индексируются на месте, поскольку возможны legacy aliases.

Доступ к одному ID сериализован фиксированными полосами RLock. Общая блокировка
защищает файл и адресацию, не выполнение потребителя. Произвольный вложенный
доступ к разным ID из нескольких потоков может инвертировать блокировки;
потребитель обрабатывает одну запись за раз. Владелец закрывает storage после
всех обращений; повторное закрытие безопасно.

`release(id)` ждёт завершения обращения из другого потока. Вызов внутри
активного `read()` / `edit()` того же ID или его десериализации в текущем потоке
запрещён и вызывает `RuntimeError`. Повторный вызов для удалённого ID и вызов
после закрытия storage безопасны и ничего не делают.

`SuiteRef` освобождает потерявшие владельцев записи через очередь cleanup.
Сборка мусора внутри pickle callback или активного обращения не удаляет запись
немедленно и не ждёт чужих блокировок. Очередь обрабатывается после завершения
операций; занятые записи сохраняются до безопасной точки. Закрытие владельца
по-прежнему обязательно.

Завершение обращения передаёт cleanup-запрос текущему drainer, даже если другой
поток уже обрабатывает очередь. Повторный проход выполняется при новом запросе,
а не непрерывно для занятой записи. Ошибка отложенного удаления диагностируется
в логах и оставляет запись pending: она не меняет результат основной операции
и не подменяет её исключение. После устранения причины удаление повторяется;
`close()` освобождает ресурсы и при оставшихся pending-записях. Явный `release()`
по-прежнему сообщает ошибку своему caller; `KeyboardInterrupt` и `SystemExit`
при cleanup не подавляются.

Pickle hooks и extractor метаданных не должны обращаться к тому же storage.
Повторный вход из такого callback в текущем потоке вызывает `RuntimeError`
до захвата блокировок, включая обращения к другим ID, вставку и закрытие.
Это ограничение действует при загрузке, подготовке snapshot и извлечении
метаданных; обычные вложенные `read()` / `edit()` / `replace()` в коде
потребителя разрешены. Ошибка callback снимает состояние подготовки;
неудачная вставка не публикует запись и не расходует ID.

Коллекции `Suites` сохраняют ту же защиту до входа, выхода и возобновления
своих context managers и итераторов: отклонённый callback не разрушает scope.
UID ссылки читается из текущих метаданных, включая вложенный edit и изменения
resident aliases. Экспорт получает UID и pickle из одного snapshot, под общей
блокировкой записи; отдельного кэша UID в ссылке нет.

Обычные клиенты используют `suites.Suites` — выборки общих ссылок поверх этого
контракта. Новые модели выбирают in-memory, любой custom-context — disk, без env.
Файловая загрузка custom-context передаёт записи напрямую из SAX в disk storage
и индексирует по одной модели; карты всех pickle-строк в памяти не создаются.
Общий `add_serialized()` остаётся ленивым, если caller не запрашивает metadata.
Это отдельный контракт от автономного `immutable.SuiteStore`: его working copies
по-прежнему не сохраняются. Доставка артефактов не зависит от способа хранения.

## Чтение отчётами без write-back

`Suites.const_iterator()` заимствует read-only views: прямые и вложенные изменения
запрещены, произвольные bound methods модели не выдаются. Чтение не сериализует
модель и не обновляет индекс. `work_dir()` вычисляется без изменения ленивого
кэша исходного объекта. При раннем выходе генератор закрывается явно.

`report_iterator()` — адаптер для потребителей, присваивающих UID старым
skipped-дескрипторам. Для такой модели он открывает mutable scope; остальные
модели выдаёт как read-only views. Дефолтный `__iter__` остаётся mutable для
потребителей, которым нужно сохранять изменения. Для передачи данных за пределы
заимствования используют самостоятельные контейнеры, а не views модели.

Read-only контейнеры сохраняют семантику equality и hash исходных значений:
представления изменяемых list/set остаются неhashable, tuple/frozenset сохраняют
исходный hash. Операции множеств возвращают повторно итерируемые read-only
результаты; membership принимает и исходные элементы, и выданные views.

Рекурсивный freeze и специализированные адаптеры моделей реализованы вместе
в `views.py`. Модули `readonly` и `suite_views` сохраняют публичные точки входа
и зависят только от общей реализации, не друг от друга. Чтение вложенных
атрибутов не выполняет ленивые импорты адаптеров.

Генератор JSON-отчёта использует const-доступ. Его выходные записи содержат
самостоятельные стандартные контейнеры, которые могут пережить заимствование;
views модели не попадают в очередь отчёта. Нормализация путей применяется к
записям отчёта, а не к общей модели. Исключение для старых skipped-дескрипторов
без UID сохраняет прежнее присваивание UID через mutable scope.
